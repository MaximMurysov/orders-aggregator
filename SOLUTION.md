# Этап 1: деньги, миграция и защита версий

Это промежуточное решение этапа 1. Новые поля ответа daily-totals, исправление DST,
полный запуск mock API с sync/webhook playback и настоящий result.json ещё не выполнены.

## Изменения и решения

- Добавлена миграция `002_order_payments.sql`: фактически оплаченная сумма хранится
  в `amount_paid_kop BIGINT`. Сумма до скидки остаётся в `amount_kop`.
  Процент валидируется, но отдельно не хранится: для статистики достаточно исходной
  и фактически оплаченной сумм; скидка будет их разностью.
- Источник фактической оплаты — `amountPaid`, без пересчёта по проценту.
  Денежные числа и десятичные строки переводятся в целые копейки через десятичные
  цифры, без умножения двоичного float. Отклоняются нечисловые, отрицательные,
  бесконечные суммы и суммы, выходящие за `Number.MAX_SAFE_INTEGER` копеек.
- Сохранено действующее правило из исходного кода и тестов: дробная копейка
  отбрасывается, например `10.999` → `1099`, `1.005` → `100`. Правило округления
  не менялось; устранена потеря целой копейки для `0.29`, `1.13`, `19.99`.
- Проверяется диапазон процента 0..100 и соотношение `0 <= amountPaidKop <= amountKop`.
  База дополнительно проверяет диапазон оплаты и безопасный размер денежной суммы.
  Полная скидка с оплатой 0 допустима для всех трёх статусов.
- Для совместимости старый payload без `amountPaid` и с отсутствующим/нулевым
  процентом трактуется как заказ без скидки. Если процент положительный, а оплаты
  нет, payload отклоняется. Явный `null` оплатой не считается. При расхождении
  процента и оплаты используется фактическая оплата, а не вычисленная оценка.

## Миграция существующих записей

В старой схеме оплата неизвестна. Миграция сохраняет исходную сумму и `updated_at`,
оставляя `amount_paid_kop = NULL`: достоверно восстановить оплату из gross нельзя.
Первое поступление той же версии после миграции может заполнить отсутствующее
поле и возвращает `updated`. Далее равная версия возвращает `stale`.
Более старая версия не применяется даже при неизвестной оплате.
Перед использованием net в следующих этапах исторические записи нужно обогатить
повторным sync/replay; неизвестную оплату нельзя молча выдавать за gross.
Ошибки старого перевода gross в копейки также исправляются при повторной загрузке
такой записи, а не выдуманным SQL-backfill.

## Причины дефектов и доказательства

1. `Math.floor(rub * 100)` работает с двоичной дробью: для `0.29` произведение
   меньше 29, для `1.13` — меньше 113. Десятичное преобразование сохраняет эти
   копейки. Регрессии покрывают числа, строки, экспоненциальную запись, отсечение
   дробной копейки и границы безопасного целого.
2. Между исходными `SELECT` версии и безусловным upsert другой запрос мог записать
   более свежий заказ. Проверка перенесена в `ON CONFLICT DO UPDATE ... WHERE`:
   версия проверяется PostgreSQL под блокировкой строки, вместе с денежными полями
   и статусом. Возвращаемые `created/updated/stale` определяются результатом записи;
   признак вставки берётся из `RETURNING (xmax = 0)` и проверен на PostgreSQL 16.
3. Тест гонки удерживает блокировку строки, дожидается двух ожидающих записей через
   `pg_stat_activity`, затем снимает блокировку. Новая версия применяется, следующая
   за ней устаревшая получает `stale` и не меняет оплату/статус. Отдельно проверены
   восемь одновременных повторов и webhook во время получения страницы sync.

В коде daily-totals также обнаружено использование смещения таймзоны на текущую
дату для всех исторических заказов. Это кандидат на причину мартовской жалобы;
доказательство на данных c_7 и исправление с тестами Europe/Berlin относятся
к следующему этапу. Реальные мартовские суммы на этом этапе не получались.

## Проверки

Проверки выполнены с помощью Codex, без замены PostgreSQL моками:

- Исходный `npm.cmd run typecheck` — успешно.
- Исходный `npm.cmd test` после запуска PostgreSQL — 27/27.
- `docker compose up -d postgres` — запущен предусмотренный проектом PostgreSQL 16.
- `npm.cmd run migrate` в локальной БД orders — применены `001_init.sql` и
  `002_order_payments.sql`.
- Итоговый `npm.cmd run typecheck` — успешно.
- Итоговый `npm.cmd test` — 70/70, 6 файлов, без пропусков.
- Миграция проверена и на старой непустой схеме в отдельном транзакционном
  namespace с rollback; проверены сохранность версии, неизвестная оплата,
  ограничения БД и отсутствие повторного применения миграций.
- Исходные тесты daily-totals и времени проходят без изменений.

Первый запуск тестов без работающей БД завершился ошибкой подключения; после
запуска compose тесты выполнены полностью. В Windows используется `npm.cmd`,
так как системная политика запрещает запуск `npm.ps1`.

При первой проверке каталог проекта не содержал `.git`, поэтому изменения
просмотрены через `git diff --no-index` относительно копий исходных файлов вне
каталога сдачи. Перед публикацией создан локальный Git-репозиторий: исходное
состояние восстановлено в начальном коммите из сохранённых копий через индекс,
без перезаписи рабочих файлов. Этап 1 оформлен отдельной веткой
`feature/stage-1-money-versioning` для проверки и последующего слияния в `main`.
Зависимости, секреты, .env, интерфейс OrdersApi и сигнатура createContainer не менялись.
